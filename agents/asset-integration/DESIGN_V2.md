## 1. 목적과 범위

이 문서는 실제 이미지가 없는 Slice 0~2에서 화면 구조와 자산 소비 계약을 검증하고, 이후 승인된 이미지가 들어와도 UI와 콘텐츠 데이터가 파일명 변경에 종속되지 않도록 2차 자산 통합 설계를 제안한다.

검토 기준은 다음 문서다.

- `docs/00_PM_MASTER_SPEC.md`
- `docs/01_LOCKED_GAME_RULES.md`
- `docs/07_UI_UX_SPEC.md`
- `docs/09_ASSET_MANIFEST.md`
- `docs/10_DECISION_LOG.md`
- `docs/11_OPEN_QUESTIONS.md`
- `agents/asset-integration/BRIEF.md`
- `agents/asset-integration/PROPOSAL.md`

이 설계는 자산 제작 지시서가 아니다. 캐릭터 외형, 표정 시트, CG 구도, 최종 배경, 이미지 생성 프롬프트, 픽셀 크기와 종횡비를 확정하지 않는다. 승인된 React·TypeScript·Vite·CSS Modules 스택과 GitHub Pages 하위 경로 배포 결정을 소비하지만 코드 구조나 패키지 추가를 승인하지 않는다.

### 1.1 최신 PM 계약 정렬(결정 046)

아래 원안과 충돌할 경우 이 절이 우선한다. Vite `base`는 `./` 단일값이다. manifest path 검증 뒤 `appBaseUrl = new URL(import.meta.env.BASE_URL, document.baseURI)`, 이어서 `assetUrl = new URL(validatedPath, appBaseUrl)`를 각각 정확히 한 번 수행한다. 현재 surface·route 문자열로 base를 추측하지 않는다.

- `https://example.test/LoveChemistry/`와 `https://example.test/LoveChemistry/index.html?x=1#top`에서 `assets/ui/a.webp`의 기대 URL은 모두 `https://example.test/LoveChemistry/assets/ui/a.webp`다.
- `https://example.test/`에서는 `https://example.test/assets/ui/a.webp`다.
- 선행 `/`, `public/`, `.`·`..` segment, 역슬래시, protocol·host, query·hash, 빈 path, duplicate slash, trailing slash를 거부한다.
- 대소문자를 정규화하지 않고 manifest path와 build artifact를 문자 단위 exact case로 비교한다.

이는 잠금 변경이나 구현 승인이 아니며 코드·production build 검증은 아직 `NOT TESTED`다.

## 2. 구체 설계

### 2.1 Slice 0~2 원칙

Slice 0~2에서는 바이너리 이미지 파일을 만들거나 요구하지 않는다. 구조 검증에는 CSS와 실제 텍스트로 렌더링하는 외형 중립 플레이스홀더를 사용한다.

| 대상 | Slice 0~2 권고 표현 | 금지 표현 |
|---|---|---|
| 캐릭터 영역 | 단색 또는 기본 테두리 컨테이너와 `캐릭터 영역`, 논리 ID 같은 중립 텍스트 | 사람 실루엣, 성별·체형·머리·복장 암시 |
| 배경 영역 | 단색 면과 `배경 준비 중`, 장소명 텍스트 | 교실·옥상 등의 미승인 구도나 최종 미술 암시 |
| CG·갤러리 | 카탈로그가 있으면 스포일러 안전 상태 텍스트, 없으면 정상 빈 상태 | 가짜 잠금 슬롯, 이벤트·캐릭터·Ne 존재나 항목 수를 추측하게 하는 구도와 문구 |
| 아이템 | 항목명 첫 글자 또는 일반 텍스트 배지 | 최종 아이템 외형이나 희귀도 표현 |
| UI 장식 | HTML/CSS 선, 면, 텍스트 | 래스터 UI 프레임, 이미지 안의 텍스트 |

플레이스홀더 문구는 외형이 아니라 영역의 기능과 준비 상태만 설명한다. 장식용 플레이스홀더는 보조 기술에서 중복 낭독하지 않고, 정보가 필요한 경우에는 화면의 실제 텍스트가 그 역할을 담당한다.

### 2.2 자산 소비 흐름

자산 소비자는 파일 경로나 확장자를 직접 알지 않는다. 흐름은 다음 순서를 따른다.

1. 화면·장면·아이템 데이터가 논리 자산 ID만 요청한다.
2. 매니페스트 조회가 해당 ID의 선언 여부, 종류, 상태, 연관 대상을 확인한다.
3. resolver가 현재 상태에서 로드 가능한 항목인지 판정한다.
4. 로드 가능하면 Vite 배포 기준 경로와 매니페스트 상대 경로를 결합한 공개 URL을 반환한다.
5. 로드 불가, 누락, 형식 불일치, 네트워크·디코드 실패이면 종류별 CSS/텍스트 fallback을 반환한다.
6. UI는 성공·대체 결과를 표시하되 게임 규칙, 해금 상태, 과학 사실을 바꾸지 않는다.

논리 ID와 파일 경로는 분리한다. 같은 ID의 파일명·확장자·해상도가 바뀌어도 소비 데이터는 바뀌지 않아야 한다. 반대로 파일이 존재한다는 이유만으로 매니페스트에 없는 경로를 추측하거나 디렉터리를 탐색하지 않는다.

### 2.3 상대 경로 resolver 계약

resolver의 입력과 책임은 다음으로 제한한다.

- 입력: 논리 ID, 선택적 용도 문맥, 매니페스트 한 항목, Vite가 제공하는 배포 기준 경로
- 출력: 로드할 공개 URL 또는 명시적인 fallback 결과와 사유
- 검증: ID 존재, `kind`, `status`, 상대 `path`, 허용 형식, fallback 순환 여부
- 비책임: 파일 자동 발견, 해금 판정, 스포일러 판정, 자산 승인, 게임 상태 변경, 네트워크 재시도 정책 추측

`path`는 항상 다음 조건을 만족해야 한다.

- 선행 `/`가 없다.
- `public/` 접두어가 없다.
- 프로토콜, 호스트, 쿼리, 해시를 포함하지 않는다.
- `.` 또는 `..` 경로 구간과 역슬래시를 포함하지 않는다.
- 실제 파일명과 확장자의 대소문자가 정확히 일치한다.
- URL 인코딩 전의 저장 값으로 관리하며 공백과 비 ASCII 파일명은 사용하지 않는 방향을 권고한다.

resolver는 1.1절의 두 단계 URL 해석을 사용한다. 저장된 `path`에 저장소명이나 Vite `base`를 중복 삽입하지 않으며, 현재 surface 또는 브라우저 라우트 문자열을 기준으로 해석하지 않는다.

### 2.4 Vite `base`와 `public` 경로 책임

| 책임 주체 | 책임 | 금지 |
|---|---|---|
| 빌드·배포 설정 | Vite `base: './'`로 문서 위치 기준 상대 산출물 생성 | 매니페스트 각 항목에 저장소명을 주입 |
| Asset Integration | `public/` 아래 저장소 위치와 선행 `/` 없는 공개 상대 `path`의 일치 검수 | `public/`을 런타임 URL에 포함 |
| resolver | Vite의 확정된 배포 기준 경로와 `path`를 결합 | `base`를 자체 상수로 복제하거나 현재 URL에서 추측 |
| Frontend | 논리 ID를 요청하고 resolver 결과를 표시 | JSX·CSS·콘텐츠 데이터에 `/assets/...` 또는 저장소 절대 경로 하드코딩 |
| QA | 루트 기준과 저장소 하위 경로 기준 빌드를 각각 검증 | 개발 서버 성공만으로 Pages 경로 합격 판정 |

`public/assets/...`는 저장소 안의 소스 위치이고 `assets/...`는 매니페스트의 공개 상대 경로다. Vite는 `public`의 내용을 산출물 루트로 복사하지만, 실제 브라우저 URL의 루트는 Vite `base` 아래다. 이 세 개념을 하나의 문자열로 혼합하지 않는다.

Slice 0~2의 CSS/텍스트 플레이스홀더에는 공개 파일 경로가 없으므로 resolver가 네트워크 URL을 만들지 않는다. 이 원칙은 바이너리 없는 초기 검증을 가능하게 하고 잘못된 가짜 이미지 경로의 404를 방지한다.

### 2.5 fallback 계약

fallback은 오류 은폐가 아니라 진행 가능성과 진단 가능성을 동시에 보장해야 한다.

| 실패 유형 | 사용자 표시 | 진단 분류 | 동작 |
|---|---|---|---|
| 요청 ID가 매니페스트에 없음 | 요청 종류를 알 수 있으면 종류별 중립 placeholder, 아니면 공통 텍스트 placeholder | `unknown-id` | 화면 진행 유지, 개발·QA 오류 기록 |
| 항목 상태가 로드 불가 | 해당 종류의 CSS/텍스트 placeholder | `not-integrated` | 네트워크 요청 없음 |
| `path`가 비었거나 규칙 위반 | 해당 종류의 CSS/텍스트 placeholder | `invalid-path` | 잘못된 URL 생성 금지 |
| 형식과 확장자 또는 실제 인코딩 불일치 | 해당 종류의 CSS/텍스트 placeholder | `format-mismatch` 또는 `decode-failed` | 다른 실제 자산으로 임의 대체 금지 |
| 404·네트워크 실패 | 해당 종류의 CSS/텍스트 placeholder | `load-failed` | 현재 화면 유지 |
| fallback 자체가 잘못됨 | 코드에 내장된 최종 텍스트 placeholder | `fallback-failed` | 재귀 해석 중단 |

종류별 fallback은 `character`, `background`, `cg`, `item`, `ui`의 의미를 보존하되 외형을 묘사하지 않는다. fallback이 다른 매니페스트 ID를 가리키는 방식을 향후 허용하더라도 자기 참조와 순환 참조는 실패로 처리하고 최종 텍스트 placeholder에서 종료한다.

CG의 잠금 상태와 파일 실패는 별개다. 미해금 CG는 실제 경로를 요청하지 않고 비스포일러 잠금 UI를 표시한다. 해금된 CG의 파일 로드가 실패한 경우에만 `이미지 준비 중` 또는 동등한 오류 placeholder를 표시하며, 숨겨진 캐릭터·이벤트 ID를 사용자 문구에 노출하지 않는다.

### 2.6 유연 컨테이너 계약

Slice 0~2에서 이미지의 최종 비율을 가정해 고정 크기 슬롯을 만들지 않는다.

- 컨테이너는 부모 폭, 사용 가능한 높이, 대화·선택지 길이에 따라 축소·재배치될 수 있어야 한다.
- VN에서는 대화와 선택 조작성이 이미지 영역보다 우선한다. 작은 화면이나 낮은 화면에서 이미지 영역은 축소 또는 비표시할 수 있지만 화자명·본문·선택지는 유지한다.
- 향후 스프라이트는 반신 표현을 수용하되 얼굴 위치, 발 위치, 좌우 여백을 현재 고정하지 않는다.
- 배경과 CG는 컨테이너를 채울 수 있지만 잘림 정책은 자산별 `fit`·안전 영역 계약이 승인된 뒤 결정한다.
- 원본 `width`·`height`는 레이아웃 고정값이 아니라 비율 계산, 품질 검수, 변형 선택을 위한 메타데이터로만 사용한다.
- `200%` 확대, 긴 한국어 대사, 큰 안전 정수 호감도, 모바일 세로·가로에서 자산 컨테이너가 핵심 동작을 가리지 않아야 한다.
- 실제 이미지 통합 때 `contain`과 `cover` 중 하나를 전역 기본값으로 강제하지 않고 자산 용도별로 승인한다.

### 2.7 preload 유예

Slice 0~2에는 바이너리 이미지가 없으므로 이미지 preload를 구현하지 않는다. preload 목록, 우선순위, 동시 요청 수, 메모리·용량 예산, 반응형 변형 선택도 실제 자산 목록과 파일 용량이 승인될 때까지 유예한다.

향후 검토 원칙만 다음과 같이 예약한다.

- 앱 전체, 전체 루트, 전체 갤러리를 시작 시 선로딩하지 않는다.
- 현재 화면에 필수인 소수 자산과 바로 다음 전이가 확정된 자산만 후보로 삼는다.
- 잠긴 CG와 히든 Ne 관련 자산은 preload 요청 이름만으로도 스포일러가 될 수 있으므로 해금·문맥 판정 전에 요청하지 않는다.
- preload 실패도 일반 로드와 같은 fallback 계약을 따르며 게임 진행이나 상태 커밋을 막지 않는다.
- 실제 전략은 저속 네트워크, 모바일 메모리, 파일 크기 측정 결과를 바탕으로 별도 승인한다.

## 3. 매니페스트 구조

### 3.1 단일 원본과 레코드 단위

런타임 매니페스트는 논리 ID를 키로 갖는 단일 정본이어야 한다. 동일 ID를 화면별 파일에 복제하지 않는다. 파일 형식은 구현 단계에서 정하되 다음 의미를 손실 없이 보존한다.

| 필드 | 필수 | 계약 |
|---|---:|---|
| `id` | 예 | 영문 소문자·숫자·점·밑줄만 사용하는 안정 논리 ID. 확장자와 경로를 포함하지 않음 |
| `kind` | 예 | `character`, `cg`, `background`, `item`, `ui`, `placeholder` 중 하나 |
| `status` | 예 | 아래 생명주기 상태 중 하나 |
| `path` | 조건부 | `integrated` 바이너리 자산에서 필수. 선행 `/`와 `public/` 없는 공개 상대 경로 |
| `format` | 조건부 | `path`가 있을 때 필수. 실제 인코딩과 일치 |
| `width`, `height` | 조건부 | 실제 파일 검수 뒤 양의 정수. Slice 0~2 가상 placeholder에는 없음 |
| `placeholderId` | 조건부 | 향후 매니페스트 기반 fallback을 쓸 때 동일 또는 호환 종류의 ID. Slice 0~2는 종류별 가상 fallback으로 생략 가능 |
| `associations` | 예 | 정규화된 연관 대상 목록. 빈 목록 허용 |
| `source` | 실제 자산 시 필수 | 출처 식별 정보. 공개 URL 자체가 아니라 검수 가능한 출처 기록을 가리킴 |
| `rightsStatus` | 실제 자산 시 필수 | 사용 권한 확인 상태. 승인 전 런타임 통합 금지 |
| `spoilerLevel` | CG·민감 자산 시 필수 | 사용자 노출·preload·진단 메시지 제한에 쓰는 분류. 해금 규칙 자체는 아님 |
| `altOwner` | 정보성 자산 시 필수 | 대체 설명 문안의 승인 책임 역할. 실제 문안은 Narrative·UI 계약에 따름 |
| `notes` | 아니요 | 승인·교체·검수에 필요한 비런타임 메모. 게임 규칙 저장 금지 |

`source`, `rightsStatus`, `spoilerLevel`, `altOwner`를 런타임 번들에 모두 노출할 필요는 없다. 제작·검수 원본과 공개 런타임 projection을 분리할 수 있으나 논리 ID와 상태 의미가 달라져서는 안 된다.

### 3.2 status 계약

기존 네 상태 이름을 유지하되 로드 가능 여부를 명확히 한다.

| 상태 | 의미 | 경로 허용 | 런타임 로드 |
|---|---|---:|---:|
| `placeholder` | 외형 중립 대체 표현. Slice 0~2에서는 CSS/텍스트 가상 항목 | 선택 | 바이너리 경로가 없으면 네트워크 로드하지 않음 |
| `proposed` | 후보 자산 또는 예상 슬롯이 있으나 승인되지 않음 | 선택 | 금지 |
| `approved` | 내용·권리·스포일러 검토는 승인됐으나 저장소 배치와 파일 검증이 완료되지 않을 수 있음 | 선택 | 금지 |
| `integrated` | 파일 배치, 경로, 형식, 치수, 권리, 기본 로드 검증이 완료됨 | 실제 자산은 필수 | 허용 |

`approved`와 `integrated`를 같은 의미로 취급하지 않는다. 런타임이 실제 바이너리 URL을 반환할 수 있는 상태는 `integrated`뿐이다. 상태 변경은 단방향을 기본으로 하지만 결함 발견 시 이전 상태로 내릴 수 있고, 그 사유와 영향 ID를 검수 기록에 남긴다.

Slice 0~2에서 화면이 요청할 미래 자산 ID를 미리 선언하는 경우 `proposed`로 두고 경로를 필수화하지 않는다. 해당 요청은 CSS/텍스트 fallback으로 수렴한다. CSS/텍스트 placeholder 자체는 파일이 아니므로 `format`, `width`, `height`가 없다.

### 3.3 association 계약

기존 `associationIds`의 문자열 목록은 ID namespace와 관계 의미가 모호하므로, V2에서는 각 연관을 `type`, `id`, 선택적 `role`의 의미 단위로 관리할 것을 권고한다.

| 항목 | 계약 |
|---|---|
| `type` | `character`, `event`, `location`, `item`, `scene`, `galleryEntry`처럼 참조 도메인을 명시 |
| `id` | 해당 도메인의 정본 ID를 그대로 참조. 자산 매니페스트가 새 콘텐츠 ID를 만들지 않음 |
| `role` | `subject`, `speaker`, `setting`, `reward`, `thumbnailFor`처럼 필요한 경우에만 관계 역할을 명시 |

연관 정보는 검색·검수·교체 영향 분석용 메타데이터다. 다음 의미를 갖지 않는다.

- 자산이 연결됐다는 이유만으로 장면, 루트, CG가 해금되지 않는다.
- 캐릭터 연관이 있다는 이유만으로 해당 캐릭터의 외형·성격·과학 사실을 정의하지 않는다.
- 연관 순서가 렌더링 z-index, 주연 우선순위, 엔딩 우선순위를 뜻하지 않는다.
- `spoilerLevel`이나 연관 ID를 사용자에게 그대로 표시하지 않는다.

하나의 스프라이트는 정확히 하나의 캐릭터를 `subject`로 연결하는 것을 기본으로 한다. 배경은 장소를 `setting`으로, CG는 승인된 이벤트 또는 갤러리 항목을 연결할 수 있다. 정확한 CG 목록과 이벤트 ID가 유예 상태이므로 Slice 0~2에서는 이를 발명하지 않는다.

### 3.4 ID와 경로 예시 규칙

기존 규칙을 유지한다.

- 캐릭터: `character.{characterId}.neutral`
- 배경: `background.{locationId}.{variantId}`
- CG: `cg.{association}.{eventId}`
- 아이템: `item.{itemId}`
- UI: `ui.{uiAssetId}`
- placeholder: `placeholder.{kind}`

`neutral`은 예약 표현 ID일 뿐 최종 표정 디자인이나 표정 시트를 확정하지 않는다. Slice 0~2에서는 위 ID를 CSS/텍스트 슬롯 식별에 사용할 수 있지만 실제 파일 경로를 만들지 않는다.

## 4. 충돌

### 4.1 바이너리 placeholder 계약 충돌

`docs/09_ASSET_MANIFEST.md`는 `placeholder.character` 등 공통 placeholder에 `.webp` 예정 경로를 부여하고, 파일이 없을 때 소비 측이 해당 논리 ID로 매핑하도록 정한다. 이번 V2는 Slice 0~2에서 바이너리 이미지 없이 CSS/텍스트 placeholder를 사용하도록 권고한다.

- 영향: `path` 필수성, placeholder 로드 방식, 누락 파일 QA 기대가 달라진다.
- 잠금 규칙 영향: 없음. 오히려 외형 유예와 이미지 생성 금지를 더 강하게 보존한다.
- 권고: PM 승인 후 `docs/09`에서 Slice 0~2 placeholder를 가상 렌더러로 허용하고 예정 WebP 경로를 미래 통합 예시로 낮춘다.
- 승인 전 처리: 본 설계만으로 `docs/09`를 대체하지 않는다. 코드 구현도 시작하지 않는다.

### 4.2 association 필드 형태 충돌

`docs/09`의 `associationIds`는 평면 문자열 목록이지만 V2는 namespace와 역할을 구분하는 `associations` 의미 구조를 권고한다.

- 영향: 매니페스트 스키마와 검증 규칙 변경이 필요하다.
- 잠금 규칙 영향: 없음.
- 권고: 아직 실제 매니페스트 데이터와 외부 소비자가 없으므로 호환 계층 없이 V2 구조를 채택한다. 기존 데이터가 생겼다면 PM이 마이그레이션 필요성을 다시 판단한다.

### 4.3 `approved` 상태의 해석 충돌 가능성

기존 문서는 상태 이름만 정의하고 실제 로드 가능 시점을 명시하지 않는다. 팀별로 `approved`를 로드 가능으로 해석하면 승인됐지만 배치되지 않은 파일에 요청을 보내는 문제가 생긴다.

- 권고: `integrated`만 로드 가능으로 고정한다.
- 영향: 승인과 저장소 통합 사이에 fallback이 보일 수 있으나 404보다 상태가 명확하다.

## 5. 타협

### 5.1 CSS/텍스트 placeholder와 실제 비율 검증

- 장점: 이미지 생성 없이 외형 유예, 접근성, 오류 상태, 핵심 흐름을 검증할 수 있다.
- 한계: 실제 스프라이트·CG의 크롭, 투명 여백, 디코드 비용, 아트 안전 영역은 검증할 수 없다.
- 타협: Slice 0~2에서는 컨테이너 유연성과 극단 화면 크기만 검증하고, 실제 자산 승인 후 별도 시각 회귀·성능 게이트를 둔다.

### 5.2 경로 단순성과 다중 해상도

- 현재는 논리 ID당 단일 경로 의미만 설계해 resolver를 단순하게 유지한다.
- `srcset`, DPI, 모바일·데스크톱 변형은 실제 파일 크기와 품질 요구가 없는 상태에서 미리 확정하지 않는다.
- 향후 변형이 필요하면 파일명 추측이 아니라 매니페스트의 명시적 variants 계약으로 확장한다.

### 5.3 preload 성능과 스포일러·복잡성

- 초기 preload를 생략하면 첫 실제 이미지 전환 때 지연 가능성이 있다.
- 반대로 지금 전략을 고정하면 존재하지 않는 파일, 메모리 예산, 히든 자산 노출을 추측하게 된다.
- 타협: Slice 0~2는 preload를 유예하고 실제 자산 샘플과 용량 예산이 생긴 후 현재·다음 문맥 한정 전략을 측정해 승인한다.

## 7. QA 리스크

### 7.1 누락 검증

- 콘텐츠가 참조하는 모든 논리 ID가 매니페스트에 선언됐는지 검사한다.
- `integrated` 항목은 `path`가 있고 빌드 산출물에 정확히 한 파일이 존재하는지 검사한다.
- 매니페스트에는 있으나 어떤 콘텐츠에서도 참조되지 않는 항목을 경고하되, preload나 갤러리용 예약 자산인지 구분한다.
- 미해금 CG는 누락 검사를 위해 사용자 UI에서 경로를 요청하지 않는다. 정적 검증과 런타임 노출을 분리한다.
- 알 수 없는 ID, 로드 불가 상태, 404, 디코드 실패 각각에서 화면이 깨진 이미지 아이콘이나 빈 클릭 영역 대신 지정 fallback을 표시하는지 확인한다.
- fallback ID를 도입하면 자기 참조, 2개 이상 순환, 호환되지 않는 `kind` 연결을 실패로 판정한다.

### 7.2 형식 검증

- 확장자, 선언 `format`, 파일 시그니처의 세 값이 일치하는지 검사한다. 이름만 `.webp`인 다른 인코딩을 허용하지 않는다.
- `width`·`height`가 실제 디코드 치수와 일치하고 양의 정수인지 확인한다.
- PNG 예외는 투명도 등 승인 사유가 있는지 확인하고, WebP 기본 원칙을 조용히 우회하지 않는다.
- SVG를 쓰게 되면 외부 참조, 스크립트, 이벤트 핸들러, 실행 가능 콘텐츠가 없는지 별도 검사한다.
- 손상·부분 파일, MIME 오표기, 브라우저 디코드 실패에서도 fallback과 오류 분류가 동일하게 작동하는지 확인한다.

### 7.3 대소문자 검증

macOS의 기본 파일 시스템에서는 대소문자 오류가 로컬에서 통과하고 GitHub Pages의 대소문자 구분 환경에서 실패할 수 있다.

- 매니페스트 `path`와 Git에 기록된 실제 경로를 문자 단위로 비교한다.
- `H/neutral.webp`와 `h/neutral.webp`, `.WebP`와 `.webp`, `classRoom`과 `classroom`을 서로 다른 경로로 취급한다.
- 같은 경로를 대소문자만 달리해 등록하는 항목을 차단한다.
- 디렉터리와 파일명은 소문자 규칙을 적용하고, 대소문자만 바꾸는 rename이 Git에 정확히 기록됐는지 통합 시 확인한다.
- 개발 서버뿐 아니라 실제 GitHub Pages와 같은 저장소 하위 `base`의 production build에서 요청 URL을 확인한다.

### 7.4 경로·배포 검증

- 프로젝트 Pages의 하위 경로와 루트 배포를 각각 모사해 같은 논리 ID가 올바른 URL로 해석되는지 확인한다.
- `path`의 선행 `/`, `public/`, 저장소명 중복, `..`, 역슬래시, 프로토콜 포함을 실패로 처리한다.
- 페이지 새로고침, 무라우터 화면 전환, 시험 주기율표 오버레이 왕복 후에도 URL이 현재 화면 경로에 상대적으로 틀어지지 않는지 확인한다.
- CSS와 콘텐츠 데이터에 `/assets/` 하드코딩이 남지 않았는지 검사한다.
- `base` 끝 슬래시와 `path` 시작 형태가 달라도 중복 슬래시 또는 경로 누락이 생기지 않아야 한다.

### 7.5 상태·연관·스포일러 검증

- `proposed`와 `approved` 항목이 네트워크 요청되지 않고 fallback으로 수렴하는지 확인한다.
- `integrated`인데 권리 상태, 형식, 치수 검증이 빠진 항목을 통합 실패로 처리한다.
- 모든 association이 존재하는 정본 도메인 ID를 참조하고 타입이 맞는지 확인한다.
- association이 게임 해금, 엔딩, 호감도 또는 과학 사실을 변경하지 않는지 확인한다.
- 미해금 CG와 Ne 관련 자산의 ID·경로·오류 문구가 사용자 화면, 접근 가능한 이름, preload 요청에서 스포일러를 노출하지 않는지 확인한다.
- 홈에서만 갤러리가 접근 가능하고, 활성 게임에서는 자산 로드 성공 여부와 무관하게 갤러리를 열 수 없는지 확인한다.

### 7.6 레이아웃·접근성 검증

- 바이너리 이미지가 0개인 상태에서도 Slice 0~2 핵심 화면을 완료할 수 있어야 한다.
- CSS/텍스트 placeholder가 외형, 성별, 체형, 복장, 표정, CG 사건을 암시하지 않는지 수동 검토한다.
- 모바일 세로·가로, 200% 확대, 긴 텍스트에서 placeholder 컨테이너가 대사·선택지·제출·복귀 동작을 가리지 않는지 확인한다.
- 장식 placeholder의 중복 대체 텍스트를 방지하고, 정보성 상태는 실제 텍스트로 전달한다.
- 로드 성공과 실패를 색상만으로 구분하지 않는다.

- 잠금 영향: 없음.

### CR-AI-03: association 구조 정규화

- 변경 대상: `associationIds`
- 요청: 도메인 namespace와 관계 역할을 구분하는 `associations` 의미 구조로 대체한다.
- 이유: 캐릭터·이벤트·장소 ID 충돌을 막고 교체 영향과 스포일러 검수를 가능하게 하기 위해서다.
- 잠금 영향: 없음.

### CR-AI-04: Vite `base`·`public`·resolver 책임 추가

- 변경 대상: `docs/09_ASSET_MANIFEST.md`와 필요시 배포 관련 승인 문서
- 요청: 매니페스트에는 `base`와 `public/`을 저장하지 않고, 빌드 설정이 `base`, Asset Integration이 상대 경로, resolver가 둘의 결합을 책임진다고 명시한다.
- 이유: GitHub Pages 저장소 하위 경로에서 절대 경로와 이중 접두어 오류를 막기 위해서다.
- 잠금 영향: 없음. 기존 GitHub Pages 잠금 요구를 구체화한다.

### CR-AI-05: preload 결정 유예 기록

- 변경 대상: `docs/09_ASSET_MANIFEST.md` 또는 후속 Asset Integration 제안
- 요청: 실제 파일 목록·용량·스포일러 정책이 승인되기 전에는 preload를 구현하지 않는다고 기록한다.
- 이유: 근거 없는 전체 선로딩, 모바일 메모리 낭비, 히든 자산 노출을 방지하기 위해서다.
- 잠금 영향: 없음.

## 9. 승인 게이트

이 설계 다음 단계는 코드 작성이 아니다. PM은 먼저 CR-AI-01~05의 채택 여부를 결정하고, 채택한 계약만 `docs/09`와 결정 기록에 반영해야 한다. QA는 누락·형식·대소문자·GitHub Pages 하위 경로·스포일러 테스트 가능성을 사전 검토해야 한다.

- 논리 ID 외의 파일 경로 하드코딩 없음
- 실제 이미지 preload 없음
- 누락 자산이 게임 상태·과학 사실·해금 규칙을 변경하지 않음
