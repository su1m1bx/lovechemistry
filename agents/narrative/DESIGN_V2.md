## 1. 설계 목적과 경계

이 문서는 구현 순서 Slice 0~2에서 Narrative가 무엇을 제공하고 무엇을 제공하지 않는지 정의한다. 이번 단계의 목적은 완성된 이야기를 쓰는 것이 아니라 UI, 시스템, Science가 향후 서사 콘텐츠를 안전하게 소비할 수 있는 경계를 만드는 것이다.

- 코드, 패키지, 런타임 데이터 파일을 생성하지 않는다.
- 최종 대사, 독백, 선택지 문장, 엔딩 문장을 작성하지 않는다.
- `docs/04_NARRATIVE_PLAN.md`의 30일 거시 비트와 일곱 루트 골격을 승인된 상세 콘텐츠로 승격하지 않는다.
- Slice 2 완료 전에는 개별 루트 사건, 미션, 보상, 엔딩을 추가로 상세화하지 않는다.
- 과학 사실은 `docs/02_SCIENCE_BIBLE.md`와 향후 Science 정본 데이터가 소유한다. Narrative는 참조 관계와 설명 목적만 지정한다.
- 주인공은 결정 015에 따라 남성 고정이며 이름은 사용자 입력이다. 이 사실의 서사 영향은 필요한 호칭·문법 정합성으로 최소화한다.
- Character End 즉시 판정과 시험 우선순위는 결정 020, 시험 중 제한 주기율표 조회는 결정 021을 따른다. Slice 0~2에서 이 규칙을 서사적으로 확장하지 않는다.

## 2. 구체 설계

### 2.1 공통 설계 원칙

1. **의미와 문장을 분리한다.** 먼저 UI나 장면이 전달해야 할 의미를 토큰·목적으로 정의하고, 최종 한국어 문장은 후속 콘텐츠 승인 뒤 작성한다.
2. **서사와 비서사를 분리한다.** 날짜, 페이즈, 저장, 오류, 행동 비용처럼 상태를 설명하는 문구는 시스템 카피이며 캐릭터 목소리를 입히지 않는다.
3. **사실과 해석을 분리한다.** 원소 사실은 Science 정본 참조로 표시하고, 캐릭터 모티프는 별도 서사 목적에만 둔다.
4. **표시와 판정을 분리한다.** Narrative는 화면 목적과 반응 범주를 제공할 수 있지만 phase 전이, 비용, 호감도, 미션, 엔딩을 판정하지 않는다.
5. **자리표시자는 완성 콘텐츠처럼 보이지 않게 한다.** 모든 임시 문구는 대괄호 의미 토큰으로 표시하며 출시 카피로 사용할 수 없다고 명시한다.

### 2.2 Slice 0: 비서사 UI 카피 책임과 자리표시자

Slice 0은 앱 부팅, 타이틀, 플레이스홀더 자산, 내비게이션, 데이터 로딩을 검증하는 단계다. 이 단계에는 캐릭터 장면이나 루트 서사가 필요하지 않다.

#### 카피 책임 분담

| 카피 범주 | 의미 소유자 | Narrative 책임 | Slice 0 표현 |
|---|---|---|---|
| 제품명 | 잠금 제품 문서 | 표기 일관성 확인 | 잠긴 제품명 사용 가능 |
| 새 게임·불러오기·갤러리 등 기능명 | UI/UX | 용어 일관성 검토 | 기능 라벨 또는 의미 토큰 |
| 저장 없음·손상·로딩 실패 | State/UI | 인물 비난, 허구 설정, 오해 유발 표현 방지 | `[SYSTEM_COPY:SAVE_*]` |
| 데이터 로딩·재시도 | UI/기술 계층 | 서사화하지 않도록 검토 | `[SYSTEM_COPY:DATA_*]` |
| 자산 미준비·누락 | Asset/UI | 외형을 암시하지 않는지 검토 | `[PLACEHOLDER:ASSET_*]` |
| CG 미해금 | Meta/UI | 인물·사건·조건 스포일러 검토 | `[SYSTEM_COPY:GALLERY_LOCKED]` |
| 플레이어 이름 입력 | State/UI | 이름 치환 위치와 남성 고정 안내의 최소성 검토 | `[SYSTEM_COPY:PLAYER_NAME_*]` |

#### 자리표시자 규칙

- 자리표시자는 `[범주:의미]` 형식의 편집용 토큰으로만 기록한다. 실제 출시 문장으로 간주하지 않는다.
- 캐릭터 자산 자리표시자는 `[PLACEHOLDER:CHARACTER_NEUTRAL]`처럼 준비 상태만 나타내고 머리, 눈, 체형, 키, 의상, 표정, 자세를 묘사하지 않는다.
- 주인공 자리표시자는 `[PLACEHOLDER:PLAYER]` 이상으로 세분하지 않는다. 남성 실루엣, 체격, 교복 변형을 요구하지 않는다.
- 로딩·오류 카피에 화학 농담이나 캐릭터 말투를 넣지 않는다. 오류와 게임 세계의 사건을 혼동시키지 않는다.
- 홈에서만 접근 가능한 갤러리의 미해금 자리표시자는 캐릭터명, 루트명, 사건명, 해금 조건을 노출하지 않는다.
- 음향이 없으므로 음량, 음소거, 음성, BGM을 전제하는 카피 토큰을 만들지 않는다.
- `준비 중`, `임시`, `누락`의 의미를 혼합하지 않는다. 정상 플레이스홀더와 오류 대체 상태는 서로 다른 토큰을 사용한다.

#### Slice 0 전달물

- 화면별 필요한 카피 **키 목록**과 의미 설명
- 용어표: 제품명, 새 게임, 불러오기, CG 갤러리, 이름, 타이틀 복귀
- 플레이스홀더 대체 텍스트의 의미 범주
- 스포일러·외형·음향 금지 검수 결과

최종 문장, 캐릭터별 문체, 장면 대사, 루트 암시는 전달물에 포함하지 않는다.

### 2.3 Slice 1: phase 중립 시스템 문구와 대사 없는 scene interface

Slice 1은 Day 표시, 페이즈, 점심·방과 후 행동, 귀가·Day 종료를 검증한다. 시스템이 phase 값을 소유하므로 Narrative 문구가 특정 내부 enum이나 화면 순서 계산을 소유해서는 안 된다.

#### phase 중립 시스템 문구

시스템 카피는 완성 문장 대신 다음 의미 슬롯을 소비한다.

| 의미 슬롯 | 필수 입력 | 금지 전제 |
|---|---|---|
| 현재 문맥 | Day 표시값, 표시용 phase 이름 | Narrative가 다음 phase를 계산함 |
| 가능한 행동 | Systems가 허용한 행동 목록 | 항상 점심 또는 항상 방과 후라고 가정함 |
| 잠금 이유 | 공개 가능한 reason 범주 | 숨은 루트 조건·정답 노출 |
| 행동 비용 | Systems가 제공한 비용 | Narrative가 비용을 추정함 |
| 확정 경고 | 소비되는 슬롯·아이템·재화의 공개 결과 | 호감도·엔딩 결과의 선판정 |
| 진행 결과 | 명령 성공·실패와 공개 가능한 변화 | 상태 반영 전 성공 표현 |
| Day 종료 | 종료 가능 여부와 저장 경계 결과 | 다음 Day가 항상 존재한다는 가정 |

- 같은 의미 슬롯이 아침 조회, 수업, 점심, 방과 후, 시험 전후에서 재사용될 수 있어야 한다.
- 문구는 `현재 단계`, `이 행동`, `다음 일정`처럼 문맥 주입 가능한 개념을 사용하며 특정 phase를 하드코딩하지 않는다.
- Day 10·20·30 시험일의 방과 후는 합격 뒤에만 열린다. 따라서 `다음은 방과 후` 같은 선행 확정 문구를 Narrative가 제공하지 않는다.
- Character End가 확정되면 미래 Day·시험을 예고하지 않는다. Day 30 `dayEnd`는 Day 31을 예고하지 않는다.
- 시스템 오류, 조건 미충족, 플레이어 취소를 캐릭터의 거절이나 관계 하락으로 표현하지 않는다.

#### 최종 대사 없는 scene interface

Slice 1의 장면은 대본이 아니라 다음 논리 필드의 소비 가능성만 검증한다.

| 필드 역할 | 내용 | 소유·제약 |
|---|---|---|
| 장면 식별 | 불투명한 `SceneId` 참조 | 안정 ID 타입만 정의, 실제 ID 미작성 |
| 장면 목적 | 튜토리얼, 전이, 피드백 등 비대사 목적 태그 | Narrative 제안, PM 승인 필요 |
| 문맥 | Day, phase, location의 시스템 제공 표시값 | State/Systems 소유 |
| 화자 | 화자 없음, 시스템, 또는 향후 `CharacterId` 참조 | 캐릭터 사실 재정의 금지 |
| 본문 슬롯 | `[SCENE_TEXT:목적]` | 최종 대사·독백 금지 |
| 선택 슬롯 | `ChoiceId` 참조와 선택 목적 범주 | 실제 선택지 문장·결과 판정 금지 |
| 도구 요청 | 주기율표 등 현재 문맥에서 허용된 도구 | UI/Systems 허용 결과 소비 |
| 효과 요청 | 선택된 결과 키 | Narrative가 직접 상태 변경하지 않음 |
| 완료 신호 | 장면 종료 의도 | phase 전이는 Systems가 판정 |

Slice 1 fixture가 필요할 경우 인물 대신 `system` 화자와 `[SCENE_TEXT:PHASE_CONTEXT]`, `[CHOICE_TEXT:CONFIRM]` 같은 토큰만 사용한다. 일곱 공략 캐릭터의 말투 예시, 첫 만남, 호감 반응, 루트 선택은 넣지 않는다.

### 2.4 Slice 2: Science 정본을 참조하는 학습 설명

Slice 2는 1~20 정본 데이터, 주기율표, 일곱 학습 주제를 다룬다. Narrative는 사실값을 쓰지 않고 설명의 교육 목적, 참조 키, 표현 단계만 설계한다.

#### 설명 생성·검수 흐름

1. Science가 `elementId`, `topicId`, 사실 필드와 승인된 용어를 제공한다.
2. Narrative는 설명 목적을 `정의`, `관찰`, `비교`, `추론 안내`, `오답 교정`, `학교 행동 연결` 중 하나로 지정한다.
3. 표시할 수치·명칭·배열은 정본 필드 참조로 주입한다. 서사 문서에 값을 복사하지 않는다.
4. 캐릭터 모티프가 필요하면 과학 사실 블록과 분리된 `narrativeContext`로 표시한다.
5. Science가 정확성, 범위, 단순화, 용어를 검수한다.
6. Narrative가 교과서식 장문, 인격화된 사실 진술, 연애 법칙화 여부를 검수한다.
7. QA가 정본 변경 시 설명 소비 영역이 함께 회귀 검사를 받는지 확인한다.

#### 학습 설명 참조 단위

| 참조 역할 | 허용 내용 | 금지 내용 |
|---|---|---|
| `topicRef` | 승인된 일곱 학습 주제 중 하나 | 새 교육 범위 발명 |
| `elementRefs` | 정본의 1~20 원소 ID | 20번 밖 필수 지식 |
| `factRefs` | 이름, 기호, 원자번호, 족, 주기, 전자껍질 분포, 승인 원자가전자 | 사실값 수동 복제 |
| `comparisonIntent` | 같은 족의 유사 경향, 같은 주기, 껍질 수 등 비교 목적 | 같은 족은 완전히 같다는 결론 |
| `cautionRefs` | H 비동일성, 안정성 비인격화 등 Science 주의 키 | Narrative 자체 주의 규칙 발명 |
| `masteryContext` | 숙련도에 따라 허용된 설명 깊이·도구 | 점수 보정·자동 정답 암시 |
| `narrativeContext` | 학교에서 이 지식을 사용할 상황의 범주 | 과학 사실을 감정의 원인으로 단정 |

#### 학습 설명 단계

- **숙련도 0:** 핵심 사실 기본 조회를 방해하지 않는다. Narrative 설명을 잠금 보상처럼 표현하지 않는다.
- **숙련도 1:** 용어 소개, 시험 범위 체크, 기초 오답 진단과 족·주기 필터의 목적만 설명한다.
- **숙련도 2:** 두 원소 비교, 대화 해석 단서, 미션 비정답형 힌트의 사고 과정을 지원한다. 정답 대상을 직접 지목하지 않는다.
- **숙련도 3:** 여러 조건 비교와 승인 범위 내 심화 오답 설명을 지원한다. 고급 화학으로 확장하거나 성공 결과를 보장하지 않는다.

시험 문맥에서는 결정 021에 따라 정본 기본 사실과 공간 배열·원소 상세만 사용한다. 검색, 필터, 두 원소 비교, 복합 비교, 힌트, 진단용 설명은 호출하지 않는다.

### 2.5 Slice 2 이후로 미루는 범위

- `docs/04`의 공통·개별 루트 골격을 실제 장면 단위로 분해하는 작업
- 캐릭터별 첫 만남, 함께 공부, 미션, 개인 사건, 엔딩의 상세 구성
- 실제 `SceneId`, `ChoiceId`, 미션·이벤트·보상 ID 목록

### 3.5 향후 stable ID 타입만 정의

이번 설계에서 허용하는 것은 다음 두 논리 타입뿐이다.

- `SceneId`: 한 장면 정의를 안정적으로 참조하는 불투명 식별자 타입
- `ChoiceId`: 한 선택 정의를 안정적으로 참조하는 불투명 식별자 타입

두 타입의 공통 계약:

- 표시 문구, Day, phase, 배열 순서, 캐릭터 이름을 식별 의미로 해석하지 않는다.
- 한 번 배포된 ID는 문장 수정, 화면 재배치, 번역으로 바꾸지 않는다.
- 삭제한 ID를 다른 장면이나 선택에 재사용하지 않는다.
- 저장 상태·플래그·QA fixture가 참조할 가능성을 고려해 영속성을 가진다.
- 실제 문자열 문법, 접두사, 목록, 생성 규칙은 Slice 2 이후 State·Systems·QA 검토를 거쳐 확정한다.
- 이번 문서에서는 실제 ID 예시도 만들지 않는다. 기존 `docs/04`의 사건 표기는 제안 골격이며 이 타입의 최종 값으로 간주하지 않는다.

`MissionId`, `EventId`, `RewardId`, `CharacterId`, `ElementId`, `TopicId`의 타입·값은 각 소유 계약을 소비하며 Narrative가 이번 설계에서 새로 정의하지 않는다.

## 4. 충돌

### 4.1 기존 Narrative 산출물과 Slice 2 이전 상세 금지

`docs/04`와 `agents/narrative/PROPOSAL.md`에는 이미 일곱 루트의 사건명, 체인, 미션 기능, 엔딩 비트가 제안 상태로 존재한다. 이번 지시의 Slice 2 이전 상세 금지는 해당 문서를 삭제하거나 승인 취소하라는 뜻으로 해석하지 않는다.

- 기존 내용은 배경 제안으로만 읽는다.
- Slice 0~2 fixture, UI 카피, 장면 인터페이스에 기존 루트 내용을 옮기지 않는다.
- 기존 임시 사건 표기를 stable `SceneId` 또는 `ChoiceId`로 승격하지 않는다.
- Slice 2 이전 검수의 근거로는 잠금 캐릭터·과학·시스템 경계만 사용하고 루트 내용 완성도를 평가하지 않는다.

### 4.2 마스터의 성별 pending과 결정 015

`docs/00`에는 성별 모순을 보존하라는 원문이 있으나, 후속 사용자 승인인 결정 015와 `docs/01`에 따라 남성 고정이 유효하다. 다만 성별 확정은 외형 또는 성별 고정 연애 역할의 승인으로 확대하지 않는다.

### 4.3 설명 문장 소유권

과학 설명은 Science가 사실·용어·범위를 소유하고 Narrative가 가독성·상황 연결을 담당한다. 어느 한 역할도 단독으로 최종 확정하면 안 된다. UI는 승인된 설명을 표시하되 축약 과정에서 과학적 한정 표현을 제거하지 않는다.

### 4.4 시스템 카피와 캐릭터 보이스

캐릭터 말투를 시스템 카피에 사용하면 상태 오류와 서사 반응이 혼동된다. Slice 0~2에서는 시스템 카피를 중립으로 고정하고, 캐릭터가 시스템 기능을 소개하는 연출은 상세 서사 게이트 이후 별도 검토한다.

## 5. 타협

### 5.1 자리표시자 가독성 대 완성도

- **채택:** 사람이 이해할 수 있는 의미 토큰과 짧은 목적 설명을 함께 둔다.
- **포기:** 자연스러운 출시 문장처럼 보이는 임시 대사를 쓰지 않는다.
- **이유:** 초기 사용성 검증은 가능하게 하되 임시 문구가 무검수 최종 콘텐츠로 굳는 위험을 줄인다.

### 5.2 phase 중립성 대 문맥 구체성

- **채택:** phase 표시명과 허용 행동을 State/Systems에서 주입받고 카피는 의미 슬롯을 재사용한다.
- **포기:** 페이즈마다 서정적인 전용 문구를 미리 작성하지 않는다.
- **이유:** 시험일, Character End, Day 30처럼 다음 흐름이 달라지는 상태에서 거짓 안내를 막는다.

### 5.3 과학 정본 참조 대 자연스러운 설명

- **채택:** 사실값은 정본 주입, 연결 문장만 Narrative 검수 대상으로 둔다.
- **포기:** 읽기 편의를 이유로 서사 데이터에 완성 사실 문장을 별도 복제하지 않는다.
- **이유:** 정본 변경 시 주기율표·학습·미션·시험과 설명의 불일치를 방지한다.

### 5.4 남성 설정 반영 대 주인공 구체화

- **채택:** 성별 표기가 반드시 필요한 안내·문법 정합성에만 `male`을 소비한다.
- **포기:** 남성성을 성격, 행동 규범, 연애 역할, 외형으로 확장하지 않는다.
- **이유:** 결정 015를 준수하면서 자기투영 범위와 비주얼 유예를 보존한다.

## 7. 남성 주인공 최소 영향 원칙

### 허용

- 새 게임에서 남성 고정임을 사실대로 안내한다.
- 상태의 고정값 `male`을 소비한다.
- 한국어 문장에서 성별 표기가 불가피할 때만 일관성을 확인한다.
- 사용자 입력 이름 또는 중립적 `주인공`, 학년·전학생 관계 호칭을 사용한다.

### 금지

- 머리, 눈, 피부, 체형, 키, 체중, 목소리, 교복 형태, 액세서리, 실루엣을 정한다.
- 남성이라는 이유로 적극성, 보호자 역할, 감정 표현 방식, 데이트 비용, 신체 접촉 주도권을 정한다.
- 히로인의 반응을 보편적 이성애 규범이나 남성성 평가로 설명한다.
- 외형을 전제로 하는 CG 구도, 키 차이, 손 크기, 체격 차이, 복장 묘사를 작성한다.
- 시스템 카피나 자리표시자에 남성 외형 아이콘을 필수로 요구한다.
- 성별 선택이 존재하는 것처럼 선택지·분기·대체 문구를 만든다.

### 검수 질문

- 이 문장이 `male`을 몰라도 같은 기능을 수행할 수 있는가. 가능하면 성별 언급을 제거한다.
- 남성이라는 사실이 외형·성격·관계 역할의 근거로 확대됐는가. 확대됐다면 차단한다.
- 이름 치환만으로 문장이 자연스러운가. 불필요한 성별 호칭을 추가하지 않는다.
- 자산 자리표시자가 주인공의 몸이나 옷을 상상하게 하는가. 그렇다면 중립 토큰으로 교체한다.

- [ ] 과학값을 장면·카피·설명 데이터에 복제하지 않았다.

### 시스템 경계

- [ ] phase 전이, 행동 비용, 잠금 여부를 Narrative가 계산하지 않는다.
- [ ] 시험일 방과 후, Character End, Day 30 이후 흐름을 카피가 선결정하지 않는다.
- [ ] 저장 성공 전 성공 문구를 표시하도록 요구하지 않는다.
- [ ] 호감도 80만으로 루트 성공을 표현하지 않는다.
- [ ] 시험 중 제한 도구 문맥에서 검색·필터·비교·힌트·진단을 호출하지 않는다.

### 캐릭터·과학·비주얼

- [ ] 일곱 캐릭터의 잠긴 성격·말투를 임시 카피 편의를 위해 바꾸지 않았다.
- [ ] 화학 성질을 성격이나 연애 감정의 필연으로 쓰지 않았다.
- [ ] H를 알칼리 금속과 동일시하지 않았다.
- [ ] 안정한 전자배치를 무감정·관계 불능으로 표현하지 않았다.
- [ ] O를 정답 제공 장치로, Ne를 침묵하는 장애물로 축소하지 않았다.
- [ ] 주인공과 일곱 캐릭터의 외형을 묘사하지 않았다.
- [ ] 남성 주인공에게 성별 고정 행동·연애 역할을 부여하지 않았다.

### 게이트 증빙

- [ ] Slice 0 카피 키·자리표시자 목록에 소유자와 placeholder 상태가 표시됐다.
- [ ] Slice 1 scene fixture는 시스템 화자와 의미 토큰만 사용한다.
- [ ] Slice 1 문구는 phase 표시값과 허용 행동을 외부에서 주입받는다.
- [ ] Slice 2 학습 설명은 `topicRef`, `elementRefs`, `factRefs`, `cautionRefs`로 정본을 참조한다.
- [ ] Science 검수 전 설명을 final로 표시하지 않았다.
- [ ] QA가 루트 상세나 대사 완성도가 아니라 경계 위반 여부를 검사했다.
- [ ] PM이 Slice 2 완료와 다음 Narrative 상세화 게이트를 명시적으로 승인하기 전 후속 대본 작업을 시작하지 않았다.

## 9. QA 리스크

| 위험 | 실패 양상 | 사전 검출·완화 |

| 장면 fixture의 루트 선점 | 임시 첫 만남이 정식 설정처럼 남음 | 시스템 화자와 의미 토큰만 허용하는 정적 체크 |
| stable ID 조기 확정 | 임시 사건 구조가 저장·테스트 계약으로 굳음 | Slice 2 전 실제 `SceneId`·`ChoiceId` 값 금지 |

| 시스템 오류의 관계화 | 저장·조건 실패가 캐릭터 거절처럼 보임 | 비서사 시스템 카피와 캐릭터 대사 채널 분리 |

## 10. Change Request 후보

현재 설계는 잠금 규칙 변경을 요구하지 않으므로 즉시 제출할 Change Request는 없다. 아래는 후속 설계에서 발생할 경우에만 Change Request로 승격해야 하는 후보 조건이다.

| 후보 | 발생 조건 | 영향 잠금·승인 계약 | 현재 처리 |
|---|---|---|---|
| CR-NAR-01 | Slice 0~2 검증을 위해 캐릭터 최종 대사나 루트 상세가 반드시 필요하다고 판단될 때 | 승인 게이트와 상세 대본 유예 | 의미 토큰 fixture를 우선 사용, 필요성 입증 전 기각 |
| CR-NAR-02 | 장면 복원을 위해 scene-by-scene 사용자 저장이 필요하다고 제안될 때 | Day 기반 저장 | State·QA 영향 검토 후 사용자 승인 없이는 금지 |
| CR-NAR-03 | 학습 설명을 자연스럽게 만들기 위해 Science 정본 밖 사실이나 20번 밖 원소가 필수화될 때 | 교육 범위·과학 정본 | 범위 안 대안 우선, 변경 시 사용자 승인 필요 |
| CR-NAR-04 | 남성 주인공의 외형 또는 성별 고정 연애 역할을 장면 성립 조건으로 요구할 때 | 비주얼 유예·결정 015의 최소 범위 | 외형·역할 중립 대안 우선, 승인 전 금지 |
| CR-NAR-05 | 시스템 안내를 캐릭터 대사로 통합해야만 한다고 제안될 때 | 시스템·서사 책임 분리와 캐릭터 보이스 | 중립 시스템 카피 유지, 통합은 PM·QA 사전 검토 |
| CR-NAR-06 | 실제 `SceneId`·`ChoiceId`를 Slice 2 완료 전에 고정해야 할 기술 의존성이 생길 때 | 이번 설계의 단계 게이트 | 타입만 유지하는 대안 검토 후 PM 승인 요청 |

## 11. 다음 승인 게이트

Slice 2 이후 서사 상세화를 시작하려면 다음이 모두 충족되어야 한다.

1. Slice 0의 카피 키, 소유권, placeholder 상태가 PM과 UI 검토를 통과한다.
2. Slice 1의 phase 중립 문구와 대사 없는 scene interface가 State·Systems·UI 계약과 정렬된다.
3. Slice 2의 Science 정본 참조 방식과 시험 문맥 제한이 Science 및 QA 검토를 통과한다.
4. 실제 ID 문법과 저장·테스트 참조 범위를 State·Systems·QA가 합의한다.
5. PM이 루트 장면 상세화의 범위와 대표 Slice를 별도로 승인한다.
6. 그 승인 뒤에도 먼저 장면 목적·선택 의도·과학 참조를 검토하고, 최종 대사는 마지막 콘텐츠 단계에서 작성한다.

이 게이트 통과 전 본 문서는 Ready to Code 또는 Ready for Final Dialogue의 근거가 아니다.
